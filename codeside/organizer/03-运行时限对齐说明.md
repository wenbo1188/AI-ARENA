# 运行时限对齐记录 · v1.2-dev

本次对齐策略运行的时间与资源规则。既定的三赛段等权场均胜平负积分、地图生成、武器、物理模拟和回放美术保持不变。

## 已实施

- 单 tick 上限默认 1000 ms 现实时间，同时启用每个策略进程的整局 CPU 预算 `20 × max_tick_count + 20000 ms`。标准 3600 tick 对局为 92000 ms，提前结束不改变预算；2v2 不翻倍。
- CPU 累计值来自进程用户态与内核态时间之和，涵盖启动、初始化、策略线程及客户端 JSON 处理。睡眠、管道等待和裁判计算不按现实耗时扣入 CPU 预算。Windows 使用 GetProcessTimes，Linux 使用 procfs utime+stime。
- 初始化与首个动作共享首次响应窗口，取消单独 3000 ms 宽限。init 与首个 turn 顺序入队，每位选手可独立完成首个动作，不等待另一选手的就绪。
- 任一时间超限、协议错误或进程退出均停止该策略控制；不保留“单次超时只跳过动作”的行为。比赛仍按实际游戏得分判断胜负。
- 内存默认 256 MiB。Windows 通过 Job Object 限制提交内存并限制单个进程；Linux 通过 RLIMIT_AS 限制虚拟地址空间。
- 输入改为异步写入，避免不读 stdin 的策略卡住裁判。stdout 队列上限 16 行、每行 65536 字符；stderr 最多保留 50 段、每段 4096 字符。
- 对局、循环赛、自测、提交校验和 AI 生成后的校验统一默认时限。参赛打包拒绝旧版或非标准单 tick 时限的自测报告。
- 手册 v1.4、任务书、单文件材料、三赛段协议样例、包内示范回放和登记表同步更新。对外参赛正文不添加历史赛事名称或战术提示。

## 验证与边界

Windows / Python 3.12.6 的 30 项回归检查通过，详细记录见 `verification/resource-timing-tests.txt`。起步程序三个赛段各左右出场一次、共六场 1200 tick 上限自测通过，记录见 `verification/starter-six-matches-1200.json`。压缩包独立解压、自测、提交打包、默认完整比赛和 CLI 默认值验收见 `verification/timing-release-check.json`。

CPU 限制采用约 5 ms 采样并在接受回复时复查，受操作系统计时粒度和调度影响，不是纳秒级硬实时计时。Windows 提交内存与 Linux 虚拟地址空间也不等同于同一 RSS 指标。Linux 实现仅有解析单元测试，尚未实机运行验证。不能宣称这份 Python 开发包与其他平台的比赛二进制逐帧、逐字节或资源测量完全一致。

本地 Job Object / 进程组和资源限制不是完整沙箱；进程启动与限制设置不是原子边界。独立文件隔离、禁网、CPU 核配额和整场看门狗仍由正式评测环境落实。本记录不将这些未部署项写成已完成。

## 核对依据（仅主办方）

- [历史比赛规则源码，第 17–31 行](https://github.com/MailRuChamps/raic-2019/blob/1a57e492c415dfdd39d64154090c5d33ef0875d2/docs/en/Rules.tex#L17-L31)：单 tick 1 秒现实时间、整局 CPU 公式、任一超限失去控制及内存上限。规则没有给本包的 JSON init 设置独立 3 秒预算；共享首次窗口是本包协议的对应实现。
- [Microsoft GetProcessTimes](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesstimes)：进程用户态与内核态 CPU 时间。
- [Microsoft Job Object 内存限制](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_extended_limit_information)：提交内存口径。
- [Linux procfs 文档](https://www.kernel.org/doc/html/latest/filesystems/proc.html)：进程 CPU 计时字段。
